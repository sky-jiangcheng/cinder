# 0061 共享主题的作用域归属——主题属于人，不属于工作区

- 状态：**Accepted（2026-11-13，用户按建议拍板 A：主题属于人）**
- 相关：ADR-0040（`LayerProjectCatalog`，跨项目目录层）、ADR-0059（三端行为对等门）、TODO 11.1

## 背景

跨端共享会话（ADR-0036）让同一个主题在桌面、VS Code、JetBrains 三端接着聊。深审发现一处**查实且当时无法判定对错**的分叉（TODO 11.1）：

| | 发问时带 `path` | 服务端行为 |
|---|---|---|
| JetBrains | **带**（`SharedChatSession.transportAsk`，`job.path` 来自创建时的 `transport.workspacePath()`） | 解析成项目 → 按项目作用域取证 |
| VS Code | **不带** | 全库目录（ADR-0040 的 `LayerProjectCatalog`） |

后果不是报错，而是**答案不同**：同一主题、同一句话，在一个面板里按项目取证，在另一个面板里按全库取证。用户看到的是「会话同步了、答案没同步」——这是共享会话这个功能本身的可信度问题，而不只是两个面板的不一致。

`repotory_ask` 的 `path` 是可选参数，两端调用都合法，所以**这不是谁写错了代码**，是缺一条产品决定：**一个共享主题的作用域归属于谁。**

## 决策

**共享主题属于「人」，不属于「工作区」。**

- **发问不带作用域**：三端发问一律不传 `path`（也不传 `project_id`），取证走 ADR-0040 的全库目录层。同一主题在任何一端的任何工作区发问，得到的是**同一个答案**。
- **`path` 保留「打标签」的用途，且只在创建时**：创建主题时把当时的工作区记进 `thread.path`，作为**出处标注**（「这个主题是在哪个项目里开起来的」），不参与取证。
- **作用域要收缩时，走显式参数**：如果将来需要「只在这个项目里问」，那是**一次显式的请求级参数**（面板上一个可见的开关），不是由「此刻开着哪个工作区」这种环境状态隐式决定。

## 为什么是 A 而不是「主题属于工作区」

1. **共享会话的卖点是跨端、跨机器接着聊**。把作用域绑到工作区，等于把「共享」降级成「在同一个仓库里共享」——换台机器、换个项目打开，同一个主题就换了答案，这与功能的承诺直接冲突。
2. **环境状态不能当作用域**。开着哪个工作区是用户当下在做什么，不是他在问什么。让前者决定后者，同一句话的答案会随窗口切换而变，且**不可见、不可预期**。
3. **隐式作用域会让「答案不一样」变成常态故障**。11.1 之所以成为问题，正是因为它是隐式的：用户无法解释为什么两个面板答得不同。

## 后果

- **答案范围变大**：不带作用域的问答会看到全库。ADR-0040 的全库目录层（`LayerProjectCatalog`）就是为跨项目问答设计的，它的条目预算与排序规则已经有独立测试兜着。
- **项目相关性下降**：问到某个项目专属的细节时，检索可能命中其他项目。这是 A 的代价，接受它——**用户要精准时用显式参数**，而不是让环境替他猜。
- **`thread.path` 的语义变窄**：从「作用域」变成「出处标签」。它仍然写、仍然可读，但**不再影响答案**。任何读 `thread.path` 去做取证的代码都是 bug。
- **三端必须同批改齐**：KT 去掉发问时的 `path`；TS 本来就不带（保持）；Warden 若走同一契约需同步核对。落码后 fixture 的 `scope.path` 由 skipped 升为 settled，三端 runner 各加一条断言（「发问不带作用域」是行为，不只是实现细节）。

## 未决的相邻问题（不阻塞本决策）

**标签冲突**：同一主题从两个工作区创建时，`thread.path` 记哪个？当前实现取创建时的那一个（先写先得），后续不复写。这是一个**标注**问题，不影响取证，因此不需要单独 ADR；若将来要显示「这个主题被两个工作区用过」，那是新的字段与新的决定。
