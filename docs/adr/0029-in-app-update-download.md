# ADR-0029: 应用内更新下载——弹窗进度 + 左下角卡片，永不自替换

- 状态：Accepted（**2026-10-25 落码并经浏览器端到端巡检**。`internal/service/update.go` 纯建议式检查 + 精确形状的产物筛选 + SHA256 校验；前端 `UpdateDownloadUI` 弹窗/左下角卡片双形态；导航栏徽标与设置页卡片共享同一次检查。真实 GitHub API 链路验证通过（返回「已是最新版本 v2.13.1」），下载态用拦截构造后逐项截图复验；巡检截图见 `outputs/e2e-2026-10-25/`)
- 日期：2026-10-25
- 关联：[ADR-0006](0006-scope-freeze.md)（范围冻结——本功能属桌面应用自我维护，不扩产品边界）、[ADR-0025](0025-backup-recovery.md)（本地优先、不外发的姿态在本 ADR 延伸为「不自动替换自身」）；起点 schema 不变（本 ADR 无 schema 变更）
- 用户原始诉求（2026-10-25）：「参考千问办公处理更新下载细节」——参考对象是千问办公的更新下载 UX：**弹窗进度 + 最小化到左下角卡片 + 完成弹窗 + 更新日志 + 当前版本**

## 背景

桌面应用此前只有「设置页 → 检查更新」，点完直接跳到 GitHub release 页让用户自己下载。这条路的问题：

1. **100 MB 的安装包要用户在浏览器里等**。release 页只给一个链接，下载进度、速度、剩余时间全在浏览器标签页里，而用户此时最想干的事是继续用应用。
2. **没有当前版本与更新日志**。「有没有新版本」是句谜语——用户得自己比对 tag。
3. **应用与安装包脱节**。用户得手动把下载的文件交给系统安装器，中间那一步（校验完整性）无人负责。

千问办公的处理方式值得抄：**下载在应用内进行，进度有一个弹窗，弹窗可最小化成左下角的小卡片继续陪着用户干活，下载完成给一个明确的完成弹窗（含校验结果与安装入口），全过程显示当前版本与更新日志。**

但有一件事不该抄：**应用自更新**。让一个程序替换自己，等于让一次网络传输的执行权落到运行中的代码里。

## 决策

**1. 纯建议式：只检测，绝不自动下载/安装/替换二进制。** 检测到新版本只**告知**，下载动作由用户显式触发，下载完把文件交给**系统安装器**，由用户决定何时安装。理由写在 `internal/service/update.go` 顶部：信任面。

**2. 产物筛选必须精确形状匹配。** `appAssetPattern = ^repotory-(darwin|windows|linux)-(amd64|arm64)\.(dmg|zip|tar\.gz|AppImage|deb|msi)$`。同一个 release 里还带着 `repotory-mcp-*` / `repotory-server-*` / VSIX / JetBrains zip——它们都含 "repotory" 和平台 token，**宽松子串匹配会把 MCP 服务器归档当成「应用新版本」推给用户**。无本平台产物（如 CI 不构建的 linux/arm64）→ 回落 release 页。

**3. 单一事实源：一个模块级 store。** `web/src/api/updateStatus.ts` 持有检查结论，导航栏徽标与设置页卡片共享同一次检查。两者各跑一次检查会打两次 GitHub API，且可能给出互相矛盾的结论（徽标说「已是最新」旁边卡片说「2.13.0 可用」比任何一边单独存在都糟）。失败时保留上次成功的结论——一次网络抖动不该把已知信息抹掉。

**4. 双形态进度，同一份快照。** 弹窗（主视图，100 MB 值得一个不能滚走的进度条与 ETA）与左下角卡片（最小化形态，让用户继续干活）读同一个 `api/downloadStatus.ts` 快照，**不可能出现「弹窗 62% 而卡片 41%」**。卡片挂在 app 级（`App.tsx`）而非设置页内——下载要能穿越导航。

**5. 轮询而非 Wails 事件。** 后端后台下载 + 绑定暴露状态，前端 400ms 轮询。理由是 headless server 的浏览器 UI 走 RPC 桥，那里没有 Wails 运行时事件监听者；轮询在两种运行时下行为一致。

**6. 下载完成的判定是 SHA256 校验通过。** 校验通过才提示「已校验」，未通过则如实说未校验。完成后给两个按钮：稍后（关闭）与打开安装器（交给系统）。

**7. `OpenBrowserURL` 只允许 https。** 「在系统浏览器打开下载链接」是唯一的外跳路径，协议必须锁死。

**8. 启动检查双闸门且失败静默。** 用户开关（`update_check_enabled`）+ 桌面 runtime（浏览器标签页指向 headless server 时自我维护无意义，但设置页的手动按钮仍可用）。失败静默——连不上 GitHub 的机器不该每次启动都看到一条横贯全屏的错误横幅；设置页按需重跑并在那里显示原因。

**9. runtime 分流。** `openBrowserURL` 桌面走 Wails 绑定、浏览器态走 `window.open`——headless server 的 UI 也是浏览器标签页，Wails 绑定在那里没有 ctx 必失败。

## 候选矩阵（下载怎么做）

| 方案 | 价值 | 主要风险 |
|---|---|---|
| **本决策：应用内下载 + 校验 + 交系统安装器** | 用户不用离开应用；完整性有交代；进度可见 | 应用要实现下载器与校验；仍需系统安装器兜底 |
| 应用内下载 + 自动替换自身 | 用户最省事 | **信任面问题**：运行中的代码被网络传输结果替换，且失败时应用可能半损坏地留在磁盘上 |
| 只跳 release 页（现状） | 实现最省 | 进度与校验都丢给浏览器；千问办公那种体验一点没有 |
| 走系统包管理器（brew/scoop） | 与发行渠道一致 | 绕过 SHA256SUMS 自校验；且用户未必装了对应包管理器 |

## 后果

**正面**：更新体验与千问办公对齐（弹窗进度 / 左下角卡片 / 完成弹窗 / 更新日志 / 当前版本）；下载在应用内完成并校验；不自动替换自身。

**负面（不粉饰）**：
- 应用内下载器要处理断点、大小、校验失败、取消——一份不算小的代码。
- 「交给系统安装器」这最后一步仍依赖外部程序，不是完全闭环。
- 启动检查是一次外网请求；即便失败静默，也是每次启动一次的网络尝试。

## 实现修正（落码与设计不同的事实）

1. **release notes 渲染不走 `utils/markdown.ts`**。该模块把 KaTeX 与 highlight.js 一起打进 lazy chunk；更新日志只是一段 Markdown，用它会把两个重依赖拖进更新路径。改为 `marked` + `DOMPurify` 直连。
2. **产物筛选的正则是唯一可靠依据来源**：release 资产的真实文件名（`repotory-mcp-*` / `repotory-server-*` / `repotory-vscode-*.vsix` / `repotory-jetbrains-*.zip` / `SHA256SUMS` 与 4 个 app bundle 并存）才是判据。发版后用真实 GitHub API 响应跑一遍筛选逻辑最省事。
3. **浏览器端难以自然复现「有更新」态**：本地版本即最新时检查永远返回「已是最新」。巡检办法是拦截 `POST /api/rpc` 的 `CheckUpdate` 响应构造出更新态——这条拦截只影响前端观察，不改任何产品代码。

## 修订（2026-11-03）：下载落到系统下载目录，路径与版本都看得见

一次真实使用把这套流程里的三个「用户无从判断」暴露了出来：下载完不知道文件在哪、不知道下到的是哪个版本（文件名永远是 `repotory-darwin-arm64.dmg`，每个版本一模一样）、装完 Finder 里出现两个 Repotory 图标（一个是装好的应用，一个是还挂着的 DMG 卷）。三件事都不是功能缺陷，是**信息没给**——应用什么都知道，只是没说。

**10. 下载目录改为系统的下载目录。** 原先落在应用自己的配置目录（macOS 上是 `~/Library/Application Support/repotory/updates`）。配置目录适合放**状态**，不适合放一个用户要自己找到、自己拖走安装的文件——藏在 `Library/Application Support` 里的安装包，用户永远找不到，于是「下载到哪个文件夹了」成了第一个问题。现在落在系统下载目录（macOS / Windows 为用户主目录下的 `Downloads`，Linux 优先取 `XDG_DOWNLOAD_DIR`），与浏览器下载同一个位置：用户找得到、也认得。

代价：下载目录是用户的地盘，不是应用的地盘。所以**状态另存**——`update-download.json` 仍写回应用数据目录，下载目录里不落任何应用自己的文件。

**11. 文件名带版本。** `repotory-darwin-arm64.dmg` → `repotory-2.25.0-darwin-arm64.dmg`。同名文件在每个版本里都一样，于是「下到的还是当前版本吗」只能靠猜；名字里有版本，答案就在文件名里。进度快照也开始带版本（此前 `begin()` 传的是空串，弹窗那行「版本 x.y.z」从来没有显示过）。

**12. 下载状态落盘。** 原来进度只在内存里：应用一重启，「打开安装包」就答「没有已完成的下载可打开」，而文件明明还在 Downloads。现在终态写入应用数据目录的 `update-download.json`，启动时恢复——**但只恢复文件还在的那一条**：指向已被删掉或移走的 bundle 的状态宁可丢掉，否则「打开安装包」会点在一个不存在的路径上。

**13. 路径可见，动作可见。**
- 完成弹窗显示**完整路径**（用户要的正是这个）；
- 新增「在文件管理器中显示」（macOS `open -R`、Windows `explorer /select,`、Linux `xdg-open`）；
- 设置页新增「安装信息」区块：安装路径与下载目录各一行——「装到哪了」从此有答案；
- 新增 `GetInstallInfo` 绑定，`install_path` 由运行中的二进制自报（从可执行文件向上找 `.app` 包），不写死。

**14. 安装包卷该推出就推出。** macOS 的 DMG 挂载后会一直留在 `/Volumes`，关掉窗口不等于推出，Finder 侧边栏因此多出一个 Repotory——这就是「装完出现两个图标」。现在两条路：用户手动点「推出安装包卷」（只推出**装着本应用 bundle** 的卷，用户自己挂载的磁盘镜像不受影响）；以及应用在检测到安装完成后**自动推出**——检测读的是安装目录里 `Info.plist` 的 `CFBundleShortVersionString`，也就是磁盘上的版本，而不是运行中的进程：替换 bundle 之后，运行中的进程内存里仍是旧代码，磁盘上的版本才是诚实信号。

**15. 落盘路径在下载启动时就定下来（修一处数据竞争）。** 状态落盘由下载 goroutine 的终态钩子执行，而路径原先是**在那个 goroutine 上现查**的。测试为了不碰真实用户目录，会把这个路径替换成临时目录——于是「测试收尾还原覆盖」与「下载 goroutine 读取覆盖」撞在一起，`go test -race` 报 DATA RACE；更糟的是，若 goroutine 在还原之后才读，状态会写进**真实用户目录**。现在路径与下载目录一样，**在下载启动时（调用方 goroutine）解析一次并带进 goroutine**（终态钩子也改成下载启动时安装，好让钩子带着路径）；测试覆盖变量的读写统一到一把锁下。

### 修订带来的后果

- **正面**：下载位置、版本、安装位置三者都可见可查；重启后安装包不再「丢失」；装完的磁盘镜像自动退场。
- **代价**：多了一个状态文件要写、一个安装目录版本探测循环（3 秒一次，最多 10 分钟）、一次 `hdiutil detach`；下载目录现在与浏览器共享，应用只是「放了一个文件进去」，不能再假设独占。
- **回归**：后端新增 12 例（下载目录落在 Downloads / 文件名带版本 / 进度快照带版本 / 状态落盘后重启可恢复 / bundle 已删则状态丢弃 / reveal 需要已完成下载 / 只认自己的 bundle / 没有挂载卷时不瞎 eject / 安装信息含路径 / Info.plist 版本读取 / 摘要结论也随重启保留 / **下载完成后自动落盘**）；前端新增 8 例（完成弹窗显示路径 / 完成弹窗显示版本 / 在文件管理器中显示 / macOS 提供 eject / 非 macOS 不提供 eject / 无卷可推的报告 / 推出成功的确认 / 设置页显示安装路径与下载目录）。`go test -race ./internal/service/ ./internal/app/` 连续四轮全绿。
