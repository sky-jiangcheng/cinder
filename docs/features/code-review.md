# 增量代码审查

每天看一眼收藏项目**昨日提交**里那些「编译不报错、联调也过、上线才炸」的问题。典型例子是跨项目
的 Feign 契约：A 集成了 B，A 侧的方法参数少了 `@RequestBody`，编译通过，运行时参数丢失。

判定分两层：**确定性规则先筛候选，模型只复核候选**（[ADR-0053](../adr/0053-incremental-commit-review.md)）。
默认**关**——它会读源码，开了 AI 还会把相关片段发出去。

## 为什么不是「让模型读 diff」

三个数先量过：

| 事实 | 后果 |
|------|------|
| 收藏项目单日增量 41–94 个 commit、1.4 万–4.7 万行 diff | 全量喂模型单日逾 10 万 token；更麻烦的是**不可复现**——同一个 commit 今天三条、明天两条，人就不看了 |
| A 侧那一行 `X foo(Req req);` 在 diff 里人畜无害 | 错配要到 B 侧的 `@RequestBody` 才成立，而 B 不在当天的 diff 里。让模型自由发挥，它只能猜 |
| 实测 113 个 Feign POST/PUT 方法里 38 个参数上没有 `@RequestBody` | 规则能捞到东西，但**误报率决定生死**：误报三次，这个功能就会被关掉 |

所以：规则负责「确定」，模型负责「这段代码有没有合法读法」，人负责最后的判断。

## 只报「这一天引入的」

`added` 行才算新增——一个方法三天前就有问题、今天只被缩进动过，不报。**历史债刻意不报**：
一次报出几十条存量问题，等于没有报告。

变更影响面而不是 diff 行：方法签名改了，方法体的旧行也可能是这次变更的后果。

## 首批规则（Java）

| 规则 | 抓什么 | 默认 |
|------|--------|------|
| `feign_missing_body` | Feign 方法参数是 POJO 却没有 `@RequestBody`（跨项目契约错配） | 开 |
| `feign_get_body` | `@GetMapping` 上挂了请求体——对端收不到 | 开 |
| `route_renamed` | 同一路径在 provider 侧改名，consumer 还指向旧路径 | 开 |
| `feign_arity` | 接口声明的参数数量与注解里的路径变量/请求参数对不上 | 开 |
| `swallow_exception` | `catch` 块里既不记日志也不抛，异常静默消失 | 开 |
| `tx_self_call` | `@Transactional` 方法被同一个类内部调用——代理没生效，事务不存在 | 开 |
| `sql_injection` | SQL 字符串用 `+` 拼参数 | 开 |
| `shared_date_format` | 静态共享 `SimpleDateFormat`（线程不安全） | 开 |
| `remote_in_loop` | 循环里发远程调用（N+1 网络往返） | 开 |
| `sensitive_log` | 日志里打印手机号/身份证/卡号 | **需手动开**——日志里可能本来就有，开不开由人定 |

规则只认**显式契约**（Spring Cloud Feign 注解），不猜自研封装。规则会随框架过期，所以每条都
写明它假设的框架行为。

## 报告怎么读

每条 finding 有五个字段值得看：

- **`severity`**：`high` / `medium` / `low`。
- **`verdict`**：`confirmed` = 模型复核后确认问题成立；`unverified` = 规则命中但**没人复核过**，可能这段代码本来就有合法读法。**别把 `unverified` 当成有问题**。
- **`evidence`**：命中的那几行原文，展开可见——不看证据就没法判断。
- **`skipped`**：单文件 diff 超过阈值（默认 2000 行）被跳过的文件数。**跳过是计数，不是静默丢弃**。
- **`ai_calls`**：这次审查花了多少次模型调用。0 表示纯规则跑（没配模型，或勾了「不用 AI」）。

候选为 0 时不会有任何模型调用——这是硬约束，不是优化。

## 三个入口，一份报告

| 入口 | 用法 |
|------|------|
| 桌面「代码审查」页 | 按文件分组的报告，可按严重程度过滤、展开证据行；右上角「跑一次」手动触发 |
| MCP | `repotory_review_latest`（读最近一次）、`repotory_review_run`（跑某一天，可 `dry_run` / `no_ai` / `force`） |
| CLI | `cinder-review --since yesterday [--dry-run] [--no-ai] [--json]`，给 launchd / 计划任务用（从源码构建：`go build -o bin/cinder-review ./cmd/review`） |

同一天 + 同一范围**只审一次**：幂等由 `UNIQUE(run_date, scope)` 保证，已完成时返回既有报告，
要重算才传 `force`。这条不是性能优化——重复跑会把同一批候选反复送给模型。

报告是**数据不是笔记**：落在 `review_runs` / `review_findings` 两张表，永远不进知识库。
机器产物混进「我的笔记」以后，那个语义就没了。

## 怎么开

设置 → **审查**：

| 项 | 默认 | 说明 |
|----|------|------|
| 启用 | 关 | 总开关。关着时既不跑定时任务，也不出红点 |
| 时间 | 09:30 | 每天几点审昨日提交 |
| 范围 | 全部收藏项目 | 也可以指定项目 |
| 用 AI 复核 | 开 | 关掉就是纯规则模式，零外发 |
| 提醒级别 | 仅高危且确认 | 左侧「代码审查」图标上的红点。`全部` / `关闭` 可选 |
| 单文件上限 | 2000 行 diff | 超过则跳过并计入 `skipped` |

红点只数 `high AND confirmed`：`unverified` 不进红点，为 0 时什么都不显示。

## 明确不做

- **不做 PR 评论机器人。** Cinder 不是 CI，结论给人看，不阻断合并。
- **不做定时全量审计。** 全量是另一个问题（存量清理），不是这里的一个开关。
- **不实现 cron 表达式。** 十分钟一次的 ticker 判断「今天过点了吗、有没有今天的 done」，够用且跨平台一致。
- **不追求覆盖所有语言。** 首批只做 Java——被审的仓就是 Java。Go / TS 规则包按需再加。
